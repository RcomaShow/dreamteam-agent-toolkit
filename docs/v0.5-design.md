# DreamTeam 0.5 — Measurement-First Orchestration

## Release thesis

DreamTeam 0.5 changes the optimization target from **cheap delegation** to **measured efficient orchestration at equal quality**.

The 0.4 line remains the compatibility baseline. 0.5 adds an explicit measurement layer and routing overlay so economic decisions can be compared against the previous behavior instead of replacing it invisibly.

## Goals

1. Separate API-equivalent cost savings from total-token savings.
2. Measure root/main-model token reduction independently from whole-tree token reduction.
3. Account for Lean root executive work instead of treating it as free delegation overhead.
4. Keep token gates in shadow mode until representative paired benchmarks calibrate them.
5. Require equal-quality paired evidence before publishing savings claims.
6. Add a Codex-native adapter without copying Claude-specific hook assumptions.
7. Preserve config v2, DCP/2, CHP/2, route names, and the 0.4 compatibility router.

## Non-goals for 0.5.0

- No claim of universal cost or token savings.
- No bundled paid-inference provider executor.
- No assumption that a cheaper model necessarily uses fewer tokens.
- No hardcoded provider model hierarchy in the provider-neutral core.
- No operating-system sandbox claim.
- No automatic activation of token gates before benchmark calibration.

## Routing architecture

`dreamteam.routing.choose_route` remains the 0.4 compatibility router.

`dreamteam.routing_v05.choose_route_v05` runs the compatibility decision and then applies the 0.5 measurement rules.

### Lean executive accounting

The Lean logical chain contains a root Sonnet executive. 0.4 priced the delegated candidate around the bounded worker and verifier while rejecting explicit Lean `executive_usage`. 0.5 accepts a separate Lean executive forecast, prices it as a non-retry root component, and re-evaluates the whole-tree margin.

If 0.4 would delegate but the Lean executive forecast is missing, 0.5 falls back to direct by default with `LEAN_EXECUTIVE_USAGE_REQUIRED`.

If adding that overhead removes the configured economic margin, 0.5 falls back to direct with `LEAN_EXECUTIVE_OVERHEAD_MARGIN_NOT_CLEARED`.

### Token gates

The initial policy records:

```text
minimum_total_token_savings = 0.05
minimum_main_token_savings  = 0.15
enforce_token_gates         = false
```

These are **shadow thresholds**, not empirical promises. They become hard routing gates only when explicitly enabled. The defaults must be recalibrated from paired workloads before any production enforcement recommendation.

## Efficiency metrics

0.5 keeps the following dimensions independent:

- direct and candidate API-equivalent USD;
- direct and candidate total provider tokens;
- direct and candidate root/main-model tokens;
- normalized payload/source bytes;
- handoff token overhead;
- reread bytes;
- retries, escalations, failed attempts, and latency;
- quality parity.

A cost saving with a total-token regression is a valid **cost** result but not a **token-efficiency** result.

## Benchmark claims

`benchmark_v05` extends the strict 0.4 paired methodology.

Publication remains bucket-specific. For every reported bucket the benchmark must preserve the same task, commit, oracle, environment, timeout, cache cohort, adapter version, and configuration identity required by the 0.4 pair invariants.

0.5 exposes separate claims:

```text
cost_claim_allowed_v05
token_claim_allowed
payload_claim_allowed
efficiency_claim_allowed
```

`efficiency_claim_allowed` requires both publishable cost and token evidence. Payload reduction is reported separately because tokenizer changes can otherwise be mistaken for context compression.

Normalized payload measurements are fail-closed: missing sidecar data cannot produce a payload claim.

## Codex adapter

The Codex adapter uses project `AGENTS.md` instructions and an optional user DreamTeam skill. It does not depend on Claude Code hook event names, plugin environment variables, or Claude agent frontmatter.

When the active Codex runtime exposes child/subagent execution, bounded delegation may use DCP/2 and CHP/2. When it does not, DreamTeam remains direct while preserving the same capsule, reread, verification, and measurement discipline.

Model selection remains an adapter/provider concern. The core talks about root/main capability, bounded workers, ownership, measured usage, and quality rather than embedding transient model aliases.

## Budget semantics and remaining gap

The 0.4 SQLite ledger already supports atomic reservations, durable charges, and `reconcile()`.

Claude strict hooks currently reserve the **forecast** cost before an Agent dispatch and commit that reservation after successful completion. Because DreamTeam still has no bundled provider executor, the hook does not receive authoritative billed provider usage to reconcile during the lifecycle.

Therefore 0.5.0 must describe the strict run budget precisely:

> The runtime enforces forecast reservations and measured metadata available to the adapter. It is not yet an authoritative provider-side hard spending cap.

A future provider executor or usage callback must feed actual usage into reconciliation before DreamTeam can claim a true provider-cost hard cap.

## Validation strategy

0.5 adds focused tests for:

- independent cost/token metrics;
- cheaper-but-token-heavier rejection by token gates;
- Lean executive overhead accounting;
- 0.4 decision reversal when the missing executive overhead removes the savings margin;
- shadow versus explicitly enforced token gates;
- paired token and normalized-payload benchmark claims;
- fail-closed sample gates;
- Codex adapter installation and overwrite safety.

Existing 0.4 routing, ledger, protocol, hook, reproducibility, release, and benchmark tests remain regression coverage.

## Exit criteria for empirical savings claims

Before recommending token-gate enforcement or publishing a general savings number:

1. define representative M0/L1/L2/C3 task buckets;
2. compare a strong direct baseline against DreamTeam with identical tools and environment;
3. randomize arm order and preserve replicates;
4. use hidden or independent quality oracles;
5. collect real provider usage rather than prompt-length estimates where available;
6. collect normalized payload bytes so tokenizer changes do not distort context-compression conclusions;
7. require complete quality parity, minimum samples, positive median savings, and positive lower-tail savings per bucket;
8. publish negative-ROI buckets as well as successful buckets.

Only then should shadow token thresholds become calibrated routing policy.
